# 一起互动 AI 工具台一期需求对照功能清单

本文按《一起互动 AI 工具台第一阶段 PRD 修改版》和已确认的平台规则整理，用于后续开发、验收和差异整改。

## 1. 总体判断

当前实现属于“一期平台骨架 + 部分关键链路 + 单个客户工具接入验证 + 工具接入规范 skill 雏形”，尚未达到完整一期验收标准。

必须按以下原则继续开发：

- demo 页面只作为视觉参考，不作为业务逻辑来源。
- 所有功能必须围绕真实业务需求实现，不能用静态假数据替代。
- 所有工具必须纳入统一工作台、运行记录、项目沉淀和 AI 网关链路。
- 所有正式工具必须通过部署门禁后才能上线。
- 项目是业务容器，任务是执行单元，工具是执行手段，AI 网关是统一模型入口，产出物是项目沉淀结果。
- 前台工作台与后台管理必须拆成两个独立入口，前台面向普通业务用户，后台面向管理员和运营配置人员。
- 权限体系不能继续使用简单角色判断，下一阶段必须按 `RBAC + 组织数据范围 + 项目 ACL + 接口级权限校验` 演进，详见《AI工具台下一阶段权限与数据隔离演进设计.md》。

## 3. 平台基础功能清单

### 3.0 前后台入口拆分

一期必须拆分两个入口：

```text
前台入口：/ 或 /workbench
后台入口：/admin
```

前台工作台面向业务用户，包含：

- 登录后进入 AI 工作台首页。
- 部门工具入口。
- 项目选择与项目页。
- 工具运行页。
- 运行记录查看。
- 个人可见范围内的结果详情。

后台管理面向管理员和配置人员，包含：

- 用户管理。
- 部门管理。
- 工具管理。
- 模型/API 配置。
- AI 调用日志。
- 操作日志。
- 部署门禁。
- 系统配置。

当前实现问题：

- 前台和后台混在同一个 `App.vue` 和“配置中心”里。
- 普通用户可以看到部分后台配置入口的视觉结构，权限隔离不清晰。
- 后台没有独立入口、独立布局、独立权限守卫。

整改要求：

- 前端拆成 `/workbench` 和 `/admin` 两套路由入口。
- 后台入口必须进行管理员权限校验。
- 普通成员不能访问 `/admin`。
- 前台侧边栏只保留业务功能，不展示模型配置、用户管理、部署门禁等后台能力。
- 后台使用独立布局，可复用登录态，但导航和页面结构必须独立。

### 3.1 登录与账号

| 功能 | 必须实现标准 | 当前情况 | 差异整改 |
|---|---|---|---|
| 登录 | 账号密码登录，错误提示不泄露敏感信息 | 已实现 | 保留 |
| 退出 | 清除登录态并返回登录页 | 已实现 | 保留 |
| 当前用户 | 登录后获取用户信息、角色、部门 | 已实现 | 保留 |
| 修改密码 | 用户登录后可修改密码 | 后端有接口 | 前端入口缺失 |
| 首次登录改密 | 新建用户首次登录必须改默认密码 | 后端有 mustChangePassword | 前端未强制拦截 |
| 管理员重置密码 | 管理员可重置用户密码 | 已实现 | 需要前端提示初始密码规则 |
| 登录失败锁定 | 连续失败超过阈值临时锁定 | 已实现基础逻辑 | 需要展示锁定提示和剩余时间 |
| 禁用用户 | 禁用后不可登录或继续访问 | 登录拦截已做 | 已登录 token 未立即失效 |
| 密码安全 | 密码加密保存 | 未实现 | 后端必须改 BCrypt |

### 3.2 角色与权限

| 角色 | PRD 权限 | 当前情况 | 差异整改 |
|---|---|---|---|
| 管理员 | 用户、工具、模型、日志、部署管理 | 部分实现 | 接口需强制 ADMIN 校验 |
| 部门负责人 | 管理本部门项目、查看部门数据 | 未严格实现 | 增加部门负责人权限判断 |
| 普通成员 | 使用工具、查看参与项目 | 未严格实现 | 增加项目成员和部门权限判断 |

本节只保留一期 PRD 的角色对照。下一阶段不能按简单角色继续扩展，必须落地正式权限模型：

- 平台 RBAC：控制用户管理、部门管理、工具管理、模型配置、部署审核、日志审计等后台功能。
- 组织数据范围：控制用户能查看本人、项目、部门或全平台数据。
- 项目 ACL：控制用户在具体项目内能否查看、运行工具、下载附件、管理成员、查看 AI 日志。
- 接口级权限校验：前端隐藏入口不能作为权限依据。

必须补充权限点：

- 用户只能查看自己有权限的项目。
- 用户只能执行自己部门或项目授权的工具。
- 用户只能查看自己有权限的运行记录和附件。
- 模型 Key、部署门禁、用户管理只能管理员操作。

详细设计见：

```text
doc/一期/AI工具台下一阶段权限与数据隔离演进设计.md
```

## 4. 工具接入清单与交付口径

PRD 中列出了多个一期工具入口，但当前客户实际只提供了一个可部署工具包：消费者洞察。因此一期交付口径应调整为：

- 平台保留 PRD 中规划的工具入口和状态展示。
- 对客户已提供的消费者洞察工具完成样板接入。
- 对客户未提供代码包、静态包或服务包的工具，不以“真实接入完成”作为本次交付验收项。
- 平台必须交付工具接入规范 skill、manifest 模板、SDK/API 说明、示例工具和校验脚本。
- 后续客户每提供一个工具包，按规范进行改造、校验、部署和上线。

### 4.2 必须交付的工具接入规范 skill

当前仓库已有：

```text
developer-skill/ai-tool-integration
```

必须补齐并作为客户交付物：

```text
developer-skill/ai-tool-integration/SKILL.md
developer-skill/ai-tool-integration/references/tool-integration.md
developer-skill/ai-tool-integration/references/api-contract.md
developer-skill/ai-tool-integration/references/ai-gateway-contract.md
developer-skill/ai-tool-integration/references/postmessage-contract.md
developer-skill/ai-tool-integration/references/security-rules.md
developer-skill/ai-tool-integration/examples/static-html-tool/tool-manifest.json
developer-skill/ai-tool-integration/examples/static-html-tool/index.html
developer-skill/ai-tool-integration/scripts/validate-tool-manifest.js
```

skill 必须明确：

- `tool-manifest.json` 必填字段。
- 工具必须调用 `/api/tool-runs/start`。
- 工具必须调用 `/api/tool-runs/{runId}/finish`。
- 工具 AI 调用必须走 `/api/ai/*`。
- 工具不得直连外部模型供应商。
- 工具结果必须按 `outputSummary/outputData/files/images/tokenUsage/costEstimate` 结构回传。
- iframe 工具必须按 postMessage 协议上报结果。
- 上线前必须执行 manifest 校验。
- 未通过校验的工具只能临时演示，不能进入正式服务器路径。

## 5. 工具运行与回传机制

### 5.1 标准任务流

必须实现以下链路：

```text
选择/创建项目
-> 打开工具
-> 校验项目成员权限、工具权限和项目状态
-> 创建 tool_run(project_id, tool_id, user_id)
-> 工具调用 AI 网关
-> 工具完成并回传结果
-> 自动生成项目结果快照
-> 更新项目看板统计
-> 写运行记录、AI 日志、操作日志
```

说明：PRD 原文中的“历史结果关联项目”属于旧口径或兼容迁移能力。最新确认规则为所有工具执行必须先选择项目，成功结果自动沉淀到项目。

### 5.2 当前实现差异

| 能力 | 当前情况 | 必须整改 |
|---|---|---|
| 打开工具创建 run | 已实现 | startRun 需强制 projectId |
| 工具完成回传 | 已实现基础 finish | 需规范 outputData、附件、错误字段 |
| 工具事件记录 | events 接口仅接收不落库 | 需要 event 表记录 open/open_failed/run/run_failed/project_result_created/project_result_removed |
| iframe postMessage | 未实现 | 需要父页面监听并调用保存接口 |
| 外链工具 | 仅 window.open 方式 | 需要外链访问记录和不支持回传提示 |
| 静态工具 SDK | 有 SDK 雏形 | 需要文档化、版本化、示例化 |
