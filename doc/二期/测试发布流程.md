# 二期测试发布流程

## 源码与制品

本次发布包含工作台前后端、上游账号管理及二期中转执行扩展。源文档素材、临时渲染文件及其他未确认目录不进入发布提交。所有环境入口从个人环境文件读取，本文不保存服务器连接值。

1. 将发布范围整理为工作台源码提交，从该提交导出干净构建目录。
2. 工作台后端运行 `mvn test` 和工程 Maven 的 `-DskipTests package`；前端按锁文件安装依赖，运行 `npm test`、`npm run build`。发布完整 JAR 和完整静态目录。
3. Sub2API 上游固定到完整提交 `86f93c28ee34cc74b629dafb748bd5ac5ca8c5ea`（`v0.2.5` 标签解析结果）。从已提交的工作台目录运行扩展 `apply.py`，在独立上游仓库记录扩展后的源码提交。
4. 按固定上游 README 构建前端，后端用 Go 1.27.0、目标 Linux 架构及 `-tags embed` 构建，保留原生管理界面。发布完整中转二进制。
5. 保存工作台提交、中转完整源码提交、上游提交、构建时间、架构与三个制品的 SHA256。临时开发构建不能直接用作发布制品。

## 发布顺序

先核验 SSH 主机身份、服务状态、磁盘空间、现有制品哈希和管理接口，再进行远端写操作。测试与生产凭据、数据库、Redis 不混用。

1. 上传到独立版本目录并校验 SHA256。
2. 停止测试工作台和中转服务，保留现有完整制品及静态目录作为回滚点；仅在本次修改受限环境配置时备份原配置。发布包含数据库结构变更、数据迁移、回填或其他发布期数据写入时，先备份受影响的数据库并验证备份可读；没有这些数据库变更时，不执行数据库备份。备份仅保存在服务器受限目录。
3. 注入缺失的工作台凭据加密主密钥和中转审计密钥，保留既有密钥。确认可用员工分组；未确认可用分组时保持自动开通关闭并记录未完成项。
4. 切换完整中转制品，检查原生健康接口、扩展版本及管理员 API。
5. 切换完整工作台 JAR 与前端目录，检查健康接口、登录、权限、配额同步及页面资源。
6. 保存发布清单和验证结果。若失败，停止新服务，恢复旧完整制品及本次修改过的配置；只有执行过数据库变更且回滚需要恢复数据时，才按同一备份点恢复受影响的数据库，再启动旧版本。

原生合规承诺只使用已有确认，若新环境要求再次确认，必须获得该环境的明确授权。禁止通过数据库改值跳过确认。没有真实测试上游账号时，须区分发布成功、配置同步成功与真实模型调用验收，不能以模拟数据宣称真实上游验收通过。
